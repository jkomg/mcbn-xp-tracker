# Regression Hygiene Checklist

Concrete pre/post-change checklist for mcbn-xp-tracker, synthesized from real incidents (silent config gaps, `docker restart` vs recreate, cross-cutting sync/audit pairing) plus the codebase's own recurring conventions. Consult before and after non-trivial changes. Companion docs: [ARCHITECTURE_WEB.md](ARCHITECTURE_WEB.md), [ARCHITECTURE_BOT.md](ARCHITECTURE_BOT.md), [PROJECT_HISTORY_AND_THEMES.md](PROJECT_HISTORY_AND_THEMES.md).

**Why this exists**: not hypothetical caution — every item below traces to something that actually went wrong or almost went wrong (a 2-day-silent disabled worker, a `docker restart` that didn't actually apply a config change, a review bot catching cross-cutting sync/audit-log gaps three separate times).

## Before editing

- **Grep for every call site before changing a shared model, table, or worker — not just the one you're looking at.** This codebase pairs DB writes with audit logging and Sheets mirroring as a *convention*, not something the type system enforces; missing one call site compiles fine and looks done.
- **If touching `apps/web/app/db.py` or `db_service.py`**: check whether the entity needs a `sheets.py`/`sheets_sync.py` pairing (tab + headers + `sync_*` methods + reconcile-loop branch) and an `audit_log`/`sync_log_action` pairing on every mutation route. See [ARCHITECTURE_WEB.md](ARCHITECTURE_WEB.md)'s Sheets-mirror section for the exact 4-file pattern.
- **If touching `character_sheet.py`'s patch logic**: any new/changed spend-category handling needs both the apply path *and* the reverse path (`reverse_character_sheet_patch`) considered together — check the staleness guard (only roll back if the field still holds exactly what this spend set) still makes sense for the new case.
- **If touching character rename/delete in `db_service.py`**: `rename_character` maintains an explicit list of tables keyed by `character_name` string (not FK) that must be updated together. If you add a new such table, add it to that list — otherwise renames silently orphan it. Current list is in [ARCHITECTURE_WEB.md](ARCHITECTURE_WEB.md).
- **If adding a new bot background worker**: follow the safe pattern (`cubbySyncWorker.ts`'s post-incident fix), not the common one. Concretely: check the `enabled` flag as the literal first line of `start()`, log a *distinct* `<name>_disabled` warning (not the generic `<name>_started`) when disabled, and don't call `setInterval` at all if disabled. See [ARCHITECTURE_BOT.md](ARCHITECTURE_BOT.md)'s footgun-audit table before assuming any existing worker's "started" log means it's actually doing anything.
- **If adding Discord role/channel mention resolution or any feature the bot could exploit with its own elevated permissions**: use a curated allowlist, not "any guild role/channel." Confirmed pattern in `/rumor`.
- **If touching Discord slash-command registration**: remember PUT is a full-scope replace; switching a deployment between guild-scoped and global orphans whatever was in the other scope with no automatic cleanup. If a command "shouldn't exist," check which scope's PUT last ran, and consider that it might belong to an entirely different bot application before assuming it's a registration bug in this one.
- **Trust nothing the client claims about its own identity/state** — re-validate server-side (e.g. coterie membership, character ownership) rather than trusting a submitted ID/name, matching the existing convention.

## While implementing

- Prefer extending an existing pattern over inventing a new one — this codebase has strong, consistent conventions (see the architecture docs); a change that looks locally clean but doesn't match the surrounding pattern is more likely to be missing a pairing than to be a legitimately better approach.
- When a fix addresses one instance of a bug class (e.g. "worker silently no-ops when disabled"), **actively check sibling code for the same shape** before considering the fix done — this is how the cubby-sync fix surfaced three more workers with the identical risk. A fix that only touches the one file you were looking at is only half-done if the bug is systemic.

## Before calling a change done

- **Web changes**: run `cd apps/web && pytest -q` (44+ files, cheap) — don't rely on ad-hoc manual test-client scripts as a substitute for the real suite, even though they're useful for exploratory verification. Add a real test under `tests/` for non-trivial logic. Also `ruff check app tests`.
- **Bot changes**: run `npm run check` (lint + format:check + typecheck + test + build) from `apps/bot` — this is the single command CI gates on; don't skip typecheck, TypeScript catches whole classes of mistakes for free.
- **Anything mutating live Discord server state** (roles, channel structure, command registration, bulk permission changes): test on the dev/test guild first — see `docs/RUN_BOT_DEV.md` and [ARCHITECTURE_BOT.md](ARCHITECTURE_BOT.md). This is a standing rule, not a suggestion.
- **Anything requiring a live production config/env change on a self-hosted box**: `docker restart <container>` does **not** re-read `.env` — it restarts the existing container with whatever environment was baked in at creation. You need `docker compose up -d <service>` run from the *correct* compose project directory (a host can run multiple `docker-compose.yml` files per app, not one root compose file) — verify which compose project actually owns the running container first: `docker inspect <container> --format '{{index .Config.Labels "com.docker.compose.project.config_files"}}'`.
- **After any schema change**: remember `db.create_all()` runs before Alembic's diff on every boot, so a `CREATE TABLE`-style migration needs a hand-written `_table_exists` guard (autogenerate will produce an empty migration body against a fresh Turso DB, since `create_all()` pre-empts the diff) — see [ARCHITECTURE_WEB.md](ARCHITECTURE_WEB.md).
- **If the fix touches something with a live incident-history** (spend approval/reversal, wiki sync, cubby linking) — check whether a symmetrical case was missed: e.g. approve without a matching reverse, sync-add without a matching sync-remove, enable-flag without a matching disabled-state log. Reviewers on this repo (including an automated one) have caught this exact class of gap multiple times.
